# Healer v1 架构与技术取舍

## 要解决的问题

UI 脚本的定位方式会随页面变化失效，盲目换一个可点击元素又可能掩盖业务错误。本项目将“计划生成”“目标身份”“定位恢复”“业务断言”分开：模型可以建议，执行和业务结果必须有独立证据。

## 模块边界

| 模块 | 输入与输出 | 不负责什么 |
|---|---|---|
| Generator | 指令、只读页面快照 → 经结构和目标证据校验的 Step 列表 | 不声称全站自主探索，不执行生成的操作 |
| Step/Target | 合法操作、独立身份条件和固定断言 | 不允许任意代码字段或未知操作 |
| Runner | 步骤 → 通过或带证据的失败 | 不替用户修改业务预期 |
| Healer | 定位失败、目标约束 → 核验后的候选或明确拒绝 | 不更换目标，不修改断言，不代替业务验证 |
| 模型客户端 | 有界 HTTP 请求 → 文本、尝试记录和可得用量 | 不把失败或缺失用量当成免费 |
| 编排与报告 | 原计划副本 → 执行结果、修复建议和可回放证据 | 不覆盖原始文件，不把分析意见当测试通过 |

## 关键选择

**规则优先，模型可替换。** 目标约束足以唯一识别元素时，程序生成精确候选比再问模型更直接。模型的主要位置是页面证据辅助的计划生成和可选失败分析；自愈候选模型保留为有界扩展点。新版评估若不触发模型，明确记录未评估模型，不制造收益。

**保存计划后再执行。** 生成命令输出可复用 JSON，执行命令接收固定计划，方便审核、重跑、版本比较和接入自动检查。旧自然语言 Python 入口仍可用，但推荐两阶段命令。生成器只知道当前页证据；后续页面结构不会凭空已知。

**身份检查同时约束原定位器与修复定位器。** 原定位器恰好匹配错误按钮也必须拒绝执行；目标存在但候选表达式不正确时允许恢复到同一目标。缺少约束的旧脚本只能按原逻辑执行，不能自动自愈。

**断言是业务结论来源。** 程序区分定位、导航/环境及断言失败。断言失败不自愈；用例失败阻断后续依赖步骤。判断业务已验证还要求最后一次导航或写操作之后有断言，但无法自动证明用户提供的断言足够完整。

**建议计划与原计划分开。** 自愈修改内存副本，保留原选择器与新选择器审计，只另存建议文件，避免修复悄悄改变测试资产。

**证据有私有与摘要边界。** HTML 不展示自由错误、定位器正文和完整指令；原始计划和 trace 可含本地账号或会话，应按私有调试数据处理。脱敏不是对任意网页内容的全局隐私保证。

## 扩展方式与限制

可以注入兼容的模型接口、显式价格表，使用同一固定评估集比较不同策略；所有新增策略必须经过相同候选核验。可通过命令返回码接入其他流水线。多站点、跨框架、动态目标身份变化、图像定位及长期修复记忆没有在 v1 中得到泛化验证。

没有增加数据库管理平台或多智能体编排依赖：当前问题不需要它们，独立模块与结构化证据已经为后续扩展留出边界。模型失败可定位为模型问题，规则失败可独立复现，不依赖黑盒大流程。
