# 自愈对照评估与真实 ShopHub 验证

日期：2026-11-08。模型：现有配置 `glm-4-flash`，真实调用 `open.bigmodel.cn`，没有用固定响应代替。费用保持未知，未使用项目内历史价格表。

## 实验对象与口径

21 个固定的合成页面场景，每种模式重复 3 次，总计 189 次场景执行。三次重复不是 63 个不同场景，也不是线上随机样本。每轮 12 个存在明确正确目标的场景，其中 1 个旧定位器原本就能执行，实际需要恢复的是每轮 11 个、每种模式合计 33 次；另外 9 个场景要求拒绝自动修复。

场景包括定位属性变化、同商品多店、同店多商品、文字变化、目标删除、歧义、禁用、遮挡、只读输入、关键页面，以及无规则支持属性的模型候选场景。每个模式使用新的浏览器上下文、相同 HTML 和预先标注的正确目标。业务结果通过独立预期检查；选对元素但业务失败不算误选，单列业务失败。

## 实测结果

| 模式 | 失败后恢复 / 可恢复失败 | 恢复比例 | 含原本成功场景的业务通过 | 观察到的误选 | 模型请求 | 场景累计耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 关闭自愈 | 0 / 33 | 0% | 3 / 36 | 0 | 0 | 10.6493 秒 |
| 纯规则 | 24 / 33 | 72.73% | 27 / 36 | 0 | 0 | 20.8521 秒 |
| 规则加模型 | 30 / 33 | 90.91% | 33 / 36 | 0 | 9 | 34.3588 秒 |

三种模式均拒绝了全部 27 次必须拒绝的场景。模型请求成功 9 次，输入 1473 tokens、输出 54 tokens（token 是模型处理文本的计量单位）；请求成功不代表修复成功。耗时含页面设置、原定位尝试、自愈和重跑，不含上下文创建及回放文件导出；顺序固定，未做延迟统计显著性分析。

纯文字按钮场景三轮均返回无效选择器 `button:ok`，被候选核验拒绝。标题属性、类名场景各三次被模型恢复。原始失败样本保留，没有为提高通过率修改预期。

**解释边界：** 模型增加了 6 次恢复，但这主要体现当前规则提取属性有限；目标约束本身已能唯一识别元素，扩充文字/语义定位规则可能替代这些模型调用。本结果不能证明模型比完善的规则引擎更强，不能证明线上误修概率为零，也不能代表跨站点泛化效果。

## 实际 ShopHub 流程

使用本机 `D:/my-test-framework` 的真实 FastAPI、MySQL 与前端源码，独立临时数据库、独立本地端口，不使用接口假响应，不重置原项目数据库。

验证路径：UI 登录 alice → 将目标按钮测试标识从 `healer-before` 改为 `healer-after` → 旧定位失败 → 规则自愈到店铺 1、商品 1 的按钮 → 加购数量 2 → GET /cart 回读 → 购物车页面核验店铺商品和数量。

实测通过，接口仅返回 `(store_id=1, product_id=1, quantity=2)`，页面仅有对应一行、数量为 2。该流程使用纯规则，不能把成果归因于模型。测试后服务已终止、临时数据库删除并经 information_schema 核验。浏览器回放记录保留在本地结果目录。

## 复现

在项目根目录：

```powershell
python -m pytest -q
python -m evaluation.benchmark
python -m evaluation.benchmark --with-model --repeats 3 --max-model-calls 12
python -m evaluation.shophub --source D:/my-test-framework
```

真实模型模式需要 config/.env；默认评估不调用模型。真实 ShopHub 模式需要该源码、已安装依赖的 .venv、MySQL 服务和有建库权限的本地账号；数据库配置从 ShopHub 自己的 .env 读取。不会调用会写入固定 shop 库的 init_db，也不会调用 reset。

每次评估在 reports 下产生独立目录，包含逐场景结果、候选审计、回放 zip。可用 `python -m playwright show-trace <trace.zip绝对路径>` 查看操作前后的页面。源码与标注在 evaluation/cases.py。trace 与原始报告默认不入 Git；可能包含本地测试账号会话信息。
